# Highlight and positioning systems: source review

Research date: 2026-10-17. Scope: research only; no dependencies, product code, or upstream implementations copied. Sources were cloned read-only outside this repository and inspected at the commits below. No upstream tests, extension prototype, performance benchmark, or live Onshape acceptance was run. “Supports” below distinguishes source mechanisms from verified integration.

## Recommendation

Keep Leqad's semantic recognition and passive outline. **PROTOTYPE Floating UI DOM only if anchored explanatory UI is needed.** None of these libraries identifies the correct CAD control, distinguishes an ambiguous match, or verifies geometry. A successful tour step is not evidence that a CAD operation succeeded.

| System                 | Decision                        | Reason                                                                                                                                                    | Estimated engineering effort, excluding live-access wait                          |
| ---------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Existing Leqad outline | **ADOPT / retain**              | Already preserves pointer input and revalidates semantic identity.                                                                                        | 1–3 days to investigate remaining geometry/accessibility cases, then acceptance   |
| Floating UI DOM        | **PROTOTYPE**                   | Positioning, overflow and update primitives without imposing tour state or a modal overlay.                                                               | 2–4 days bounded prototype; 3–7 further days hardening if useful                  |
| Driver.js              | **REFERENCE ONLY**              | Good small imperative API, but core tour CSS and keyboard handling conflict with passive CAD guidance.                                                    | 2–4 days evaluation; 5–10 further days adapting and validating a tour integration |
| React Joyride          | **DEFER**                       | Strong React tour UI; duplicates lesson lifecycle and adds focus/overlay behavior unnecessary for SHOW.                                                   | 3–5 days evaluation; 5–10 further days integration                                |
| Shepherd               | **REJECT for present adoption** | More tour machinery, recurring modal work, and unresolved commercial licensing choice. Reconsider only with a clear tour need and owner-approved license. | 3–5 days evaluation; 5–10 further days integration, excluding licensing review    |

These ranges are judgment estimates for one engineer familiar with Leqad, not vendor estimates or measured implementation times. A bounded prototype is not authorization for adopting a dependency.

## Driver.js

**Mechanism and fit.** TypeScript core exposes imperative `highlight`, `refresh`, and `destroy`; no runtime dependencies are declared. React needs an effect-owned instance and teardown. The build targets ES2020; that is a compilation target, not a proven browser support matrix. Separate CSS must be loaded into the correct document. [API/lifecycle](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/driver.ts), [build](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/tsdown.config.ts).

**Input is the disqualifying default.** Core CSS disables pointer events on descendants of the active body and re-enables the target subtree and popover. The overlay catches outside clicks; click handling suppresses propagation on Driver UI. This can impede CAD canvas gestures and menus portaled outside the highlighted subtree. Making the overlay transparent does not remove these interaction rules. Its newer hints entry is a more relevant reference for nonmodal guidance, but is a different integration from core `highlight()`. [CSS](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/driver.css), [click handling](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/click.ts), [hints](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/hints.ts).

**Geometry and lifecycle.** Positioning is custom. Core refreshes through RAF on window resize/scroll, with non-capture scroll registration; nested scrolling therefore needs particular scrutiny. Hints use capture scrolling. Core events trap Tab over target/popover and use Escape/arrows; disabling keyboard navigation does not disable the separately installed Tab trap. Destruction removes listeners, overlay, classes and restores focus. Document queries and document-level class cleanup do not establish Shadow DOM support; an element reference alone does not fix styling, focus retargeting, or cleanup across roots. Tour CSS has animation without an automatic reduced-motion rule in the inspected file; disable animation explicitly if evaluated. [events](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/events.ts), [positioning](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/position.ts), [highlight cleanup](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/src/highlight.ts).

**License/weight.** [MIT license](https://github.com/nilbuild/driver.js/blob/ca44ea064a8a57ab4acb197e57c6f514d2df4da1/packages/driver/license) permits commercial distribution with notices. Zero declared runtime dependencies does not mean zero bundle or runtime cost. No comparable gzip/CPU measurement was made.

## React Joyride

**Current architecture matters.** Version 3.2.0 uses `@floating-ui/react-dom`; old advice describing react-floater/Popper is not accurate for this commit. TypeScript declarations and React 16.8–19 peers are declared. ES2022 build target and configured Chromium/Firefox/WebKit Playwright projects are evidence of intended compatibility, not executed results here. [Manifest](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/package.json), [browser configuration](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/playwright.config.ts).

**Positioning and interaction.** Floating UI middleware handles placement/overflow; target tracking listens to its scroll parent and window and observes target resizing, with cleanup. An SVG cover intercepts outside input; target blocking is separately configurable. A custom portal element allows intentional placement, but cross-root focus queries still need validation. Document selector lookup does not pierce shadow roots; explicit elements help address resolution only. Focus trapping restores prior focus and cancels its timer on cleanup. No automatic reduced-motion handling was found in the inspected `src`; scrolling/beacon animations require an explicit policy. [Floater](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/src/components/Floater.tsx), [target tracking](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/src/hooks/useTargetPosition.ts), [overlay](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/src/components/Overlay.tsx), [focus](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/src/hooks/useFocusTrap.ts), [DOM lookup](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/src/modules/dom.ts).

**CSP/license/weight.** A nonce can be placed on injected beacon/loader style elements; it is not proof that every style operation passes a host CSP. [Beacon source](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/src/components/Beacon.tsx). [MIT](https://github.com/gilbarbara/react-joyride/blob/1fe55f1aedcf6d1fe0bceaf1418c0d5ad9a65bbb/LICENSE) permits commercial use with notices. Manifest size-limit entries specify **30 kB budgets**, not measured shipped size. Several runtime utilities plus Floating UI add dependency surface; marginal WXT bundle cost remains unmeasured.

## Shepherd

**License gate.** The pinned [license file](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/LICENSE.md) contains AGPL-3.0 and the maintainer's commercial-license policy. Commercial proprietary distribution must not be assumed compatible with the free route. AGPL itself is not a blanket prohibition on commerce; the actual distribution/source obligations and the vendor's commercial terms need an owner/legal choice. Do not copy Shepherd implementation into Leqad as a way around that choice. Pricing was not established.

**Capabilities.** Typed core with an official React package; current React wrapper declares React 18/19 peers. Browser configuration targets recent Chrome/Firefox/Safari/Edge plus Edge 18, while its scripted Cypress CI target is Chrome; declarations alone do not demonstrate legacy support. [React manifest](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/packages/react/package.json), [browser targets](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/.browserslistrc).

**Geometry/overhead.** Tooltips use Floating UI autoUpdate with cleanup. The optional modal computes openings repeatedly through an active RAF loop; it cancels that loop on cleanup. It handles clipping against scroll parents and has iframe offset logic. This is concrete recurring work, not a measured performance regression. Modal CSS blocks input on the mask, and step configuration can disable target interaction. Multiple openings can help menus, but require real target/menu identity. [positioning](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/shepherd.js/src/utils/floating-ui.ts), [modal](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/shepherd.js/src/components/shepherd-modal.ts), [modal CSS](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/shepherd.js/src/components/shepherd-modal.css).

**Accessibility and roots.** Dialog keyboard handling tracks focusable descendants; tour completion restores previous focus. Ordinary document selectors remain in attachment helpers; arbitrary shadow trees are not established as supported. No reduced-motion rule was found in the inspected runtime source. Core depends on Floating UI DOM and deepmerge-ts; no extension bundle benchmark exists here. [dialog](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/shepherd.js/src/components/shepherd-element.ts), [tour lifecycle](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/shepherd.js/src/tour.ts), [attachment](https://github.com/shipshapecode/shepherd/blob/cf36267bd034a4a457148f91a00a13c68435aca6/shepherd.js/src/utils/general.ts).

## Floating UI DOM: meaningful narrower alternative

**What it supplies.** Typed geometry and middleware for offset, flip, shift, size and arrow positioning. `autoUpdate` tracks overflow ancestors, ResizeObserver and layout movement, with per-frame tracking opt-in rather than default. It returns a disposal function. Shadow-host traversal and visualViewport ancestors are implemented, and dedicated shadow DOM tests exist. These are stronger source evidence than a generic “works with any framework” claim. [update source](https://github.com/floating-ui/floating-ui/blob/defb25074a69f1d985bb7b7d96c3f2cd34868a94/packages/dom/src/autoUpdate.ts), [DOM traversal](https://github.com/floating-ui/floating-ui/blob/defb25074a69f1d985bb7b7d96c3f2cd34868a94/packages/utils/src/dom.ts), [shadow tests](https://github.com/floating-ui/floating-ui/blob/defb25074a69f1d985bb7b7d96c3f2cd34868a94/packages/dom/test/functional/shadow-dom.test.ts).

DOM positioning alone adds no modal, pointer mask, keyboard capture, animation, focus trap, or semantic recognition. That makes it suitable beneath an existing passive outline or an optional React explanation. Leqad still owns accessible content, dismissal, focus policy, reduced motion, target invalidation and cleanup. Use a real recognized HTMLElement; do not turn low-confidence coordinates into a definite semantic target. DOM avoids needing a React positioning wrapper unless the UI benefits from one.

**Compatibility/cost.** Root browser targets include Chrome 73+, Firefox 78+, Edge 79+, Safari/iOS 12+; observer availability changes behavior, so these are build intentions. DOM is tree-shakeable and declares only core/utils dependencies. Neither that nor individual website size claims predicts the actual WXT increment. [manifest/browser targets](https://github.com/floating-ui/floating-ui/blob/defb25074a69f1d985bb7b7d96c3f2cd34868a94/package.json). [MIT](https://github.com/floating-ui/floating-ui/blob/defb25074a69f1d985bb7b7d96c3f2cd34868a94/LICENSE) allows commercial use with notices.

## Cross-cutting evidence limits and Leqad comparison

**MV3/CSP:** all four can plausibly be bundled locally into a content script; that is architectural inference, not a tested compatibility claim. Library code manipulating the DOM does not belong in an MV3 service worker. Package all JS/CSS locally; validate actual WXT output, content-script isolated-world behavior, injected styles under the target page's CSP, and extension UI shadow-root placement. Joyride's nonce is useful but does not certify the whole integration. None was exercised in Onshape here.

**Real browser zoom:** a test name containing “zoom” is insufficient. Floating UI's [zoom tests](https://github.com/floating-ui/floating-ui/blob/defb25074a69f1d985bb7b7d96c3f2cd34868a94/packages/dom/test/functional/zoom.test.ts) explicitly exercise CSS zoom on body/html/containers; they even document a remaining absolute-positioning case. They do not establish toolbar zoom at 80/100/125/150/200%, pinch zoom, or CAD camera zoom. For Driver/Joyride/Shepherd, rectangle calculations and resize handling suggest compatibility, but real browser zoom is unverified. CAD camera zoom changes model projection and is a separate problem none of these DOM libraries solves.

**Existing implementation:** at Leqad `4be3602`, [semanticTargets.ts](../../apps/extension/src/services/semanticTargets.ts) (`createHighlightOutline`, `createTargetHighlight`, `createSemanticHighlighter`, around lines 670–860) already uses a fixed `aria-hidden` outline, `pointer-events:none`, reduced-motion selection, capture scroll, resize, target ResizeObserver, body MutationObserver, RAF scheduling and idempotent disposal. It invalidates hidden/disabled/disconnected targets and repeats recognition so changed identity or ambiguity clears the outline. Replacing this with a generic tour risks losing these trust properties. Existing body observation/semantic revalidation can itself be costly under large CAD DOM churn; no benchmark establishes either its cost or a library's improvement.

[Unit tests](../../apps/extension/src/services/semanticTargets.test.ts) around lines 417–590 cover ownership, changing identity, ambiguous targets, cleanup, pointer style and reduced motion. The test named “tracks scroll and zoom geometry” changes mocked rectangles and dispatches a scroll event; it is **not actual browser zoom**. [Calibration browser tests](../../apps/extension/tests/e2e/calibrated-highlight.spec.ts) explicitly use a simulated fixture, including click-through and viewport invalidation; they do not establish live CAD behavior. Existing plain-DOM lookup also does not establish shadow-root target recognition.

**Before any adoption:** compare the prototype with the existing outline on the same disposable Onshape document. Record native toolbar zoom separately from CSS zoom/device scale; nested tree scrolling, resize, dropdown portal opening, target replacement, document navigation and remount; keyboard shortcuts, canvas drag/wheel, focus preservation and reduced motion; detached observers/listeners after repeated SHOW/clear; CSP console failures; and actual production bundle increment plus idle/active CPU traces under representative DOM churn. A tooltip must disappear on stale/ambiguous recognition. These are proposed acceptance criteria, not completed results. Authenticated live Onshape acceptance remains an external gate.
