# UI recognition and Onshape implementation source review

Reviewed 2026-10-17. This is source inspection, not live Onshape acceptance. No dependencies, runtime integrations, new recorder, or proof of concept were added. Scratch clones are under `/workspace/work/research-sources/ui-review/`; only this research document is a deliverable from this investigation.

## Decision

Retain Leqad's deterministic, abstaining semantic targeting. Use Playwright as the primary architectural reference for fresh resolution, strict matching, accessibility semantics and actionability. Use Page Modeller separately as an optional developer inspection tool, not copied production code. Study Onshape MX's explicit command identity and dropdown ownership as concrete hypotheses to validate with the existing capture workflow. Do not promote its selectors or command IDs to Leqad's trusted registry solely because another extension uses them. VeraAura is an instructive tutorial implementation but is unsuitable for code reuse without a license grant. Stagehand and browser-use solve agent observation/action selection; neither supplies trustworthy CAD command semantics or model verification.

The critical distinction is between (1) an interactive node, (2) a unique locator, (3) the exact requested CAD command or group arrow, (4) an observed UI interaction, and (5) a correct model. None entails the next. Even an exact, unique `button` name can describe the current mainbutton variant rather than its group's dropdown arrow.

## Page Modeller: strong locator tooling, not CAD identity

Inspected [candidate engine][pm-candidates], [interactive collection][pm-interactive], [configuration][pm-config] and [privacy policy][pm-privacy]. The engine generates ranked locator candidates using accessible role/name, labels, text, authored attributes, CSS and XPath; computes predicted match counts; traverses open shadow roots; builds frame/shadow paths; and avoids some generated IDs. This is substantive implementation beyond a README claim. It has per-scan memoization reset after each batch, so role/name/match results are not globally cached across scans.

Useful separation: its scan visibility filter combines accessibility exclusion and rendered box, while resolver match counts track the intended locator engine's semantics. Hiding a duplicate from an authoring panel does not make a locator unique at execution time. The engine's `hasBox` accepts nonzero width **or** height, which is appropriate for discoverable page objects but is insufficient for a reliably actionable CAD toolbar target. Neither its ranking nor a unique CSS path establishes exact CAD command identity, current sketch mode, ownership of an adjacent arrow, or correct last-used variant.

MV3/WXT is directly relevant to Leqad's packaging. The config asks for `<all_urls>`, activeTab, tabs, storage and contextMenus; Chromium side panel is configured through WXT with a Chrome 114 floor. Privacy policy says no network or telemetry; inspected code/config supports local locator generation, session model storage and synchronized settings. A full network audit was not run. Generated locators may contain page text/identifiers, so using this tool on private CAD still requires restricting what is copied into reports.

**Reuse:** standalone manual development aid or architectural ideas implemented independently. Do not copy GPL engine code into an extension with an unresolved licensing/distribution policy. A GPL derivative may be commercially distributed if obligations are accepted, but that is an owner/legal decision outside this review. Do not assume generated output and copied generator implementation have identical licensing implications.

## VeraAura: real teaching overlay, insufficient verification

The [content script][va-content] implements JSON task steps, CSS or chained open-shadow queries, click/input/text-change observation, a pulsing overlay, persistence and SPA resume. [Manifest][va-manifest] is MV3 with activeTab, scripting, storage, identity, webNavigation and `<all_urls>` host access. [Background code][va-background] fetches bundled tasks and can POST learner email, task ID, completion percentage and timestamp to a configured Google Apps Script endpoint; email/endpoint are read from synchronized storage. This is not a strictly local tutor.

Specific limitations in the actual implementation:

- `findElement` returns `querySelector`'s first result. No duplicate rejection, semantic command registry, exact command proof, visibility filtering or arrow ownership validation exists there.
- Action target and highlight target can be separate selectors, but the code does not prove they belong to the same command. A visually correct highlight can coexist with an incorrect listener.
- A missing target installs a mutation observer and retries. Once a target exists, click/input listeners attach to that node. Replacing it leaves those listeners on the detached node. The animation loop hides a disconnected highlight but does not re-resolve its replacement.
- The missing-element observer is not pushed into the cleanup listener registry in that branch. A stopped/replaced step can leave a waiting observer until its target appears.
- Visibility checks only reject a rectangle whose width **and** height are both zero; they do not check occlusion, CSS visibility, enabledness or uniqueness.
- Click completion means a click event was received, with link navigation intercepted for storage. It does not establish successful operation or model state; progress percentage is not CAD verification.

**Reuse:** conceptual lesson schema/overlay lifecycle reference only. No license grant found, so no copying or vendoring. Even a later permission grant would leave target identity, stale node handling, scope, permissions and privacy work. Do not import its progress logging into Phase 1.

## Playwright: adopt invariants, keep the runtime out of the content script

The [locator implementation][pw-locator] delegates actions with strict matching and resolves selectors through the frame; it is not a long-lived element handle. The [injected implementation][pw-injected] includes strict-mode errors, element-state checks and hit-target checks. [Actionability documentation][pw-actionability] distinguishes visible, stable, receiving events and enabled conditions; strictness alone proves none of those. [Locator documentation][pw-locators-doc] explains re-resolution and open-shadow behavior. CSS/role locators can pierce open shadow roots; XPath does not provide equivalent piercing; closed roots remain an observability boundary.

[ARIA snapshot source][pw-aria] builds a structured accessible tree and traverses open shadow roots. Its names/roles/states are a valuable low-noise observation format. They are not a CAD command dictionary, not geometry, and not a durable identity scheme across rerenders. Duplicate names, omitted inaccessible controls and canvas content remain issues. Snapshot references should stay tied to one observation generation.

**Leqad transfer:** reject multiple eligible matches; scope to the active editor/tool family; re-resolve immediately before highlighting/acting; revoke prior evidence on relevant mutation/navigation; treat visibility, enabledness, freshness, identity and ownership as separate fields. Use an accessible label as identity evidence only when corroborated by a validated domain rule. Do not use `.first()`/`.nth()` to suppress uncertainty. An accessible tree cannot reconstruct an unnamed split-arrow's semantic parent by itself.

Playwright's full package assumes a browser automation driver and protocol connection. Its injected DOM helpers demonstrate browser-compatible algorithms, but copying internal files creates version coupling and transitive dependency/license obligations. Prefer existing Playwright developer tests and a small independently implemented invariant set within Leqad. Running ordinary content-script targeting needs no debugger permission; moving to automation/CDP would add an entirely different privilege and lifecycle surface.

## Other actual implementations

### Finder

[Finder source][finder-source] computes a unique CSS selector for an already chosen element using configurable ID/class/attribute rules and ancestor search. It verifies `querySelectorAll` counts; optimization also checks that the selector resolves to the original node. It supports a ShadowRoot scope. Default search timeout is 1000 ms and default maximum path-check count is unbounded, so opportunistic whole-toolbar use needs tighter budgets. It neither identifies the desired command nor checks actionability or ownership. A structural path can remain unique while pointing at a different command after rearrangement.

**Reuse:** optional development-only selector serialization after a human/semantic resolver has chosen the node, with MIT notices. Not a runtime recognition fallback. No network is required by this DOM-only utility; no browser permissions are intrinsic to the library.

### Stagehand

At this reviewed commit Stagehand has a [real MV3 runtime manifest][sh-manifest] requiring `debugger`, `offscreen`, `scripting`, `tabs`, `<all_urls>`, Chrome 116+, and content scripts in all frames. Describing this version as categorically unable to run in an extension would be incorrect. Its [hybrid snapshot capture][sh-capture] merges DOM and accessibility information per CDP session/frame, maps nodes to XPath, and supports focused/ignored subtrees. [Observe service][sh-observe] captures this representation and passes it to model inference, then converts model-selected IDs into actions; it also has cache integration.

This solves natural-language candidate selection and frame-aware representation. A model returning an action or a cached selector does not prove a CAD command, group owner or model result. A new snapshot/strict resolution and deterministic semantic gate remain necessary. Imported runtime permissions and AI/model data paths are disproportionate to Leqad Phase 1. Local browser execution does not imply local model processing: `observe` explicitly passes the tree to the configured generation path. Model/server deployment and commercial cloud terms require separate review from the MIT source license. Dependencies also include telemetry/export libraries; this review did not establish their exact enabled-by-default export configuration.

**Reuse:** architecture reference only now; reconsider for explicitly authorized later agent work. Do not add the runtime, debugger permission or model calls to the deterministic lesson.

### browser-use

[DOM service][bu-dom] obtains CDP DOM snapshots, accessibility trees and viewport data, with explicit timeout/concurrency handling; its serializer produces compact interaction-oriented representations. This is useful evidence for combining layout and semantics instead of trusting text alone. It remains a Python/browser-control stack, not a drop-in TypeScript content-script library. Indexed targets are observations, not stable CAD IDs. [Telemetry implementation][bu-telemetry] uses PostHog and supports disabling through `ANONYMIZED_TELEMETRY=False`; a no-telemetry claim would be wrong without configuration review. Model prompts/browser contents can have a separate provider data path. **Reuse:** algorithm/reference only for current scope, not dependency or cloud service.

## Actual Onshape browser integrations

### Onshape MX: deepest matching source, still not validated Leqad rules

This is a functioning implementation-shaped repository: Chrome content script/service worker, C# hardware plugin, profiles, command definitions, packaged artifacts and an author-reported tested setup. It is much stronger evidence than invented selector suggestions. It is nevertheless an unofficial third-party integration, with no PTC guarantee of private DOM stability. I found no checked-in test/spec/fixture files or CI workflows in this repository using a tracked-file search. The screenshot is of the keypad, not a sanitized DOM capture proving every CAD target. No live behavior was reproduced.

Precise locations in [content.js][mx-content]:

A bare shared ID permits multiple variants. |
| 128–161      | Context inferred from sentinel command IDs; active/disabled from classes; open dialog found by first visible match.                                               | Context is heuristic, not document scope, permissions or model evidence.                                                                      |

| 208–220      | `press` dispatches pointer/mouse events at target center.                                                                                                         | Synthetic action attempt, not acknowledgement; inappropriate to import as tutorial completion evidence.                                       |
| 223–268      | `faceOf` associates arrow with parent's first command descendant; global dropdown content query; loop opens arrows and caches option-to-face mapping.             | Concrete split-button ownership idea, but parent structure and global menu scoping must be validated.                                         |

Additional failure modes inferred from the code:

1. The `dropdownOf` Map has no explicit clear/invalidation path. Re-resolution limits stale DOM handles, but cached owner hints survive tool-family/context transitions and mainbutton changes for the document lifetime.
2. The cache maps to the **current face command ID**, not a proven stable group identity. Choosing a different rectangle variant changes that face. A hint may become wrong even while the correct arrow remains in place.
3. `openDropdownItems` queries globally, and `waitForDropdown` returns as soon as **any** visible matching menu items exist. A prior menu, unrelated visible popover, or asynchronous close/open race can be attributed to the new arrow. Waiting up to ten 30 ms intervals is a timing heuristic, not ownership evidence.
4. Both toolbar and menu use first-match selection. There is no rejection of duplicated command-bearing descendants, cloned responsive toolbar controls or duplicate live menus.
5. Bounding boxes do not exclude hidden-by-visibility, transparent, offscreen or covered controls. Center-point dispatch does not implement real hit testing.
6. Attribute identity/icon values are third-party-observed private UI details. Their presence in source proves what this project expects, not that the current account, browser, locale and Onshape release render them.
7. The code distinguishes some assembly variants with icon suffixes. This is evidence **against** assuming `command-id` alone is universally one-to-one. SVG content and assets also carry separate PTC rights; [NOTICE][mx-notice] explicitly discusses icons/trademarks.

MV3 [manifest][mx-manifest] narrows pages to `https://*.onshape.com/*`, uses alarms, a service worker, minimum Chrome 116 and loopback WebSocket host access. [Background bridge][mx-background] sends toolbar state/icons/form-related information to a local hardware plugin at port 47810. This avoids a required cloud hop but still crosses a process boundary and is not needed by a local teaching overlay. Do not copy that bridge, action dispatch or asset extraction into Leqad.

**Minimum validation before any identity rule is reused:** use the existing authorized disposable-document capture path; manually observe the mainbutton, arrow, open menu and exact item separately; record only allowlisted UI identity/ownership data; repeat after selecting a different last-used variant; distinguish absent, hidden duplicate, visible duplicate, disabled and covered cases; recheck after rerender, sketch/Part Studio transition and navigation. Establish a scoped owner relation through real attributes/structure, not proximity alone. Check Rectangle plus another split family (e.g. Circle) before claiming transfer; validate feature tools separately. Keep every unknown/ambiguous case abstaining, with no action dispatch. A sanitized capture and tests derived from it support a candidate rule; a separate live acceptance observation is still required. No new recorder or PoC is justified before this existing evidence path is used.

### Rally: internal command catalog instead of DOM heuristics

[Bridge commands][rally-commands] reads `MiniToolbarService` settings/command groups and serializes command namespace, command details, context, icon and disabled metadata; `executeCommand` calls `ElementToolbarService`. [Injector][rally-injector] reaches `window.angular.element(document).injector()`. [Event bridge][rally-events] patches `$rootScope.$broadcast`/`$emit` and forwards selected events via `window.postMessage`. This is actual Onshape-specific integration with richer semantics than a selector generator. It is also dependent on private Angular services and main-world access, not a supported public command API.

[Manifest][rally-manifest] is MV3 with storage permission, Onshape-only content matching and a web-accessible bridge script. [Privacy policy][rally-privacy] states local processing/no tracking; the reviewed bridge remains local, but this was not a full bundle network audit. Main-world events can contain application data and are accessible to page scripts; same-origin messages alone do not establish trusted model evidence. The service catalog can describe command identity without identifying which rendered split-arrow belongs to it. Its internal API calls bypass the learner's ordinary UI action flow and are unsuitable as Phase 1 teaching completion signals.

**Reuse:** reference for researching the existence of richer command metadata, not a production private-service dependency. Prefer externally observable validated DOM/ARIA contracts now. If official interfaces later supply equivalent semantics, that is a separate architecture decision.

## Teaching implementations and honest coverage limits

Onshape's [Explore Onshape help](https://cad.onshape.com/help/Content/Home/explore_onshape.htm), updated 2026-10-09, documents a real tutorial tab/panel with videos, instructions, progress, interactive exercises and a Check button. This establishes that integrated teaching/checking exists. Its checker implementation and license were not available in the reviewed public material; no claim is made about its target-recognition or geometry-check algorithm, and no source reuse is possible from a help page.

[profbrady/Teaching_Onshape](https://github.com/profbrady/Teaching_Onshape) was inspected as a search lead: its tree/README contains assignments and older curriculum PDFs, not a browser recognition implementation. It is excluded as a runtime candidate. VeraAura is the actual open-source-visible general teaching overlay reviewed above; it has no demonstrated Onshape integration. Other extension store/search results without inspected source are not counted as evaluated implementations. PTC-Education/cad-learner/model verification is assigned to the primary investigation and is not duplicated here.

Official [Onshape extension documentation](https://onshape-public.github.io/docs/app-dev/extensions/) describes iframe UI and REST action integrations, OAuth registration and origin/document validation. These are application integrations, distinct from Chrome extensions that inspect the toolbar. This documented surface does not grant access to a private DOM command catalog or establish current selector compatibility.

## Required transfer contract

A future reusable targeting rule should return exact semantic target kind (command versus group opener), current scope and generation, eligible match count, owner relation evidence, visibility/enabledness, and the basis for semantic identity. It must not reduce these to a single optimistic score. Candidates without positive identity and ownership evidence stay missing/ambiguous/unknown.

Learn the algorithm once; validate each command family independently. Shared strictness, actionability, observation-generation invalidation and owner-link mechanics transfer across Rectangle, Circle and feature tools. Actual command IDs, labels, icons, dropdown topology and context do not transfer without evidence. Canvas geometry cannot be recovered from these DOM contracts. Existing Leqad `semanticTargets.ts` and its Rectangle duplicate/ownership tests already implement parts of the required boundary; these findings support tightening that system rather than replacing it with a new general framework.
